# Closed-period named formula operands

For recurring editable or employee-varying inputs, an independent salary base or rate in a saved workbook is a typed formula operand. It is not an earning line, an amount override, the annual CTC, or a location attendance part. For example, a previous-month salary reference can remain independent of the separately reviewed current monthly CTC even when their values happen to be equal.

The existing protected closed-period template/salary workflow can also specialize a captured, explicitly reviewed numeric Information literal for one closed source month using the normal formula translator. That older-reader-compatible representation keeps the original dependency/operator proof and bounded history dates, without creating a named profile or operand manifest. It cannot infer a current CTC alias, freeze an earned output/cache, authorize another month/employee, or turn a missing input into a literal. Current/future Master and source values stay unchanged. A changed literal requires a fresh rule/source review; use typed operands when the value must remain independently editable or vary across employees/periods. The named-writer deployment gate below remains unchanged.

`Payroll:HistoricalNamedInputsEnabled` is **false by default**. An explicit historical named-input request and any historical assignment using a managed named template must pass this writer capability. `HistoricalSalaryUse` on the existing named-template configuration request also uses this capability; the existing location-template flow remains separate. Reading a previously authenticated operand does not depend on the writer flag.

Do not enable the capability or save real historical named templates/history until **every live API and payroll worker that can read the shared database supports these operands**. Older payroll readers select effective `employee_it0008_basic_pay` rows for past months and cannot resolve a newly declared formula token. A closed date range and a localhost API do not make those older readers compatible. Restarting only localhost is insufficient. Verify the deployed API and workers against the compatible release before enabling writes; keep the capability off while compatibility is unknown.

The existing protected named-template declaration defines each operand's key, purpose (`FormulaOperandOnly`), unit, precision and bounds. The review binds it to an independent literal Information cell and its actual captured header. Earned outputs, identities, attendance, formula caches, blanks and component overrides cannot supply an operand.

Historical save writes the typed values/cell evidence to a protected `named-input-h:<history ID>` sidecar. Its scope includes the exact client, employee, calendar month, effective history ID/window, unchanged annual target and component-input hash, template/declaration, original source/raw hashes, source identity, reviewer and protected salary receipt. It creates no location assignment and adds no new salary-map component.

The ordinary payroll loader resolves the sidecar from the selected effective history before reviewed PT and calculation. Changed/disabled declarations, missing manifests, source/header/cell changes, mismatched employees/months/history, or a missing/tampered receipt fail closed. The formula evaluator and traces use the authenticated operand context. The separately reviewed annual target remains unchanged.

For a composed historical PT review, the new receipt and complete named manifests are visible only inside the caller's uncommitted transaction before the actual saved-history PT basis is read. Only that newly inserted receipt is finalized after its PT evidence is assembled. The final ordinary saved Employee calculation must reproduce the reviewed amounts before commit. Any failure rolls back the new history, operand metadata, receipt, PT controls and audit rows together; existing/current/future salary records are preserved.

Absent optional reviews/manifests retain legacy request, receipt and input-fingerprint shapes. A source amount difference review is a separate explicit source-bound permission capped at INR 1; it cannot approve a missing operand, an unsupported formula, an identity or attendance gap, or an amount override. Different actual formula families require distinct reusable rule versions, not per-employee templates or a guessed common formula.

## First-source setup

The existing location-allocation setup request can explicitly bind the same protected declarations through optional `NamedInputReview`. Independent monthly component inputs keep their existing proration rules; a period quantity such as OT hours uses a truthful `Hours` operand and its dependent variable earning formula. The independently reviewed recurring monthly wage budget remains separate from variable OT earnings. Requests without the optional review retain their legacy wire/hash path.

First-source approval has its own purpose-separated protected receipt, saved in the same transaction as the ordinary Applied setup receipt, exact assignments, allocations and operand manifests. It retains the authenticated reviewer, complete original row/employee/part selection, declaration, source/raw hashes and the database-canonical request/result hashes. It does not fabricate a correction receipt or edit source profile links. The ordinary reader rechecks the receipt, declaration, captured literal cells and current strong employee ownership before using the values. Existing correction-origin manifests retain their original link requirements.

This path uses the same default-OFF compatible-reader gate. Deploy compatible API and payroll workers before enabling real writes against their shared database. A valid first-source operand receipt does not supply missing actual attendance, dates, policies or financial reconciliation and does not authorize payroll approval, payment or email.

An optional, omitted-when-absent `SourceIdentityReview` can reuse the existing explicit literal-bank identity contract for first-source named setup. It requires the original source/header/cell, exact current employee code/name, source-month eligibility and one global bank owner, rechecked during preview, locked Apply and ordinary read. The existing government-only path is unchanged when no review is supplied. Conflicting government data, changed names without a government anchor, shared/foreign accounts, imprecise/formula/error bank cells and ambiguous repeated source parts still fail. The canonical protected setup request authenticates this review without a new receipt kind or fabricated source profile link.
