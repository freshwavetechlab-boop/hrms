# Excel payslip batches and original workbooks

## Existing data and rollout

Previously the browser sent parsed worksheet/batch JSON, not the uploaded file bytes. Existing calculation sources cannot reconstruct the original workbook. Historical generated salary-template exports are not substitutes for the original upload.

This change adds original attachment retention to new imports and a guarded permanent-delete capability. It does not delete, upload, backfill, apply master setup or run payroll automatically.

The owner must review/apply the existing `--migrate-excel-payslips` migration entry point before deploying the matching API/UI. `Database/ExcelPayslips.sql` adds four tables and a global confidential attachment field; it does not drop existing data. Existing attachment tables must already exist. Do not run the migration against production as part of tests. The legacy migration's existing refusal to discard unconverted mail evidence is preserved. DDL is not transactionally reversible in MySQL: take a normal database backup and inspect migration output. Rolling back the application should retain the new tables and originals; do not drop them as an automatic rollback.

This feature's migration is explicit; page reads, saves, cleanup previews and workers do not execute its DDL or automatically clean records. Existing `Database:AutoMigrate` startup behavior invokes other legacy setup routines and has not been changed. Its deployed value is not verified here. The explicit legacy migrator removes only exact old batch keys after copy verification; unconvertible mail receipts block conversion. Additive DDL may already have completed before a legacy-conversion refusal, because MySQL DDL implicitly commits.

## Originals

* New imports retain up to 50 source workbooks via the existing `AttachmentRepository`, `entity_attachments`, storage selection, capacity checks, `AttachmentStorageService` and attachment audit. No second file store is introduced.
* XLSX, XLSM, binary XLS and UTF-8 CSV are retained passively, up to the smaller of the global attachment limit and 25 MiB. Container/signature validation and bounded ZIP metadata inspection never execute macros, formulas or external links. This is not a malware-scan claim. XLSM downloads may still contain macros; opening them is a separate user action.
* The active global original-workbook field's effective dates, allowed extensions/MIME types and size limits also apply. An added document-number/date or verification requirement blocks this upload flow instead of being bypassed. Each original has its own immutable attachment owner.
* A configured active global attachment server must accept the write. This flow excludes the system `API_LOCAL` fallback and never repairs/provisions it. If storage is unavailable, a new import is not saved.
* SHA-256 deduplication is within the client only. Each saved batch link records the upload filename; attachment metadata records content type, size, hash and uploader. Files with identical names but different bytes remain different originals. Repeated upload of identical bytes reuses the attachment.
* New corrections record their direct parent batch. Later-month calculations inherit the parent's original links. Legacy descendants can legitimately have no original because bytes were never retained.
* Raw download requires the existing payslip-management permission and active client scope, not merely register-read or recruitment attachment permissions. Downloads use the existing attachment content response, forced download, no-store and nosniff; access requests are audited. Shared raw originals cannot be deleted through generic attachment delete/purge routes.
* An interrupted upload/commit can leave an orphan physical file. An uncertain commit never triggers compensating deletion. Reconcile storage and attachment metadata manually; no broad orphan purge is implemented. An uploaded original can remain unlinked when the user cancels or saving the batch fails. Retaining it is intentional rather than risking removal of shared bytes.

## Permanent deletion

* Batch History exposes a dependency preview and explicit confirmation (exact batch ID plus acknowledgement). Backend requires payslip management **and** `settings.manage`, rechecks client scope, and recalculates dependencies under the client/batch transaction locks. A changed preview is rejected.
* Any job, send request, delivery, coordinator request, notification queue/log, master-setup receipt (including draft) or dependent calculation/correction blocks deletion. All statuses are protected; dismissing a job does not make its evidence disposable.
* Legacy batches start in review, not an automatic orphan state. The UI can verify a persisted client-scoped parent chain, or compare a newer retained version. Self/cyclic, missing and cross-client recorded ancestors cannot be accepted. Exact financial/calculation snapshots can provide duplicate evidence. Different versions require the same client/month/source/component bindings and unique employee-code coverage, followed by the operator's explicit review of the original finance source and confirmation of the retained final version. A filename or name-only match is insufficient.
* Supersession records an authorized version-retention decision; it does not reconstruct missing creation ancestry. The review receipt is separate from immutable financial/delivery snapshots. Both snapshot/source hashes are rechecked every time. If historical evidence or stable identity coverage is insufficient, the UI shows the exact prerequisite and offers no force-delete bypass. The new resolution workflow does not auto-backfill old provenance during migration.
* Only an eligible unused new or reviewed legacy batch is permanently removed: its financial JSON, calculation-source JSON and exact client/batch original links. Employee masters, salary components/templates, policy configuration, pay runs, notification attachments/evidence and shared original bytes are never cascaded. Regular pay runs do not directly reference Excel batch IDs; the persisted master-setup receipt is the bridge provenance and blocks deletion.
* Original attachment bytes are retained even when the final batch link is removed. This implements batch/version cleanup, not a file-retention-policy purge. The preview reports removed and other retained links. Audit keeps only IDs/counts/dependency token/actor/time, not deleted employee rows or amounts.
* Repeating the same successful deletion confirmation returns an idempotent result. A different confirmation token cannot claim that deletion. Client locks serialize saves/derived batches/master setup/job submission; batch locks serialize coordinator requests and state mutations. No active work is cancelled or deleted.

## Blocker resolution in the UI

Batch History's **Review / delete batch** action lists exact object IDs, states and retained reasons. Related batches can be opened for their own review; no automatic descendant cascade or reparenting occurs. Preview counts and records include notification queues/logs, jobs, delivery descriptors, request receipts, master setup, unconverted legacy storage, originals and cleanup audit.

The only destructive resolution actions are (1) an unapplied `Draft` with an empty object result and (2) a proven never-queued job with no delivery documents, matching queue/log records or successful/queued result. Its own paired unqueued request receipt is removed with it. Each action needs the exact object ID, acknowledgement and fresh token. Result/draft status and client/batch ownership are rechecked under the same transaction locks as apply/send. Applied/non-empty setup records and dispatched attempts cannot be discarded. Active/retry jobs are not cancelled; unsupported provider/evidence conversion needs a separately approved process. Dismissing a job only hides it and is not evidence deletion.

Resolution request IDs are retained on uncertain retries and audited transactionally. A repeated identical request returns its recorded result; reusing an ID for a different action is rejected. Resolution always returns a fresh preview and clears deletion acknowledgement in the UI. A new job, dependent, changed source or changed snapshot invalidates an old deletion confirmation. Final content deletion requires another separate exact-batch-ID confirmation. Cleanup receipts survive batch deletion, with hashes/counts/technical IDs rather than copied employee rows. Original attachment bytes remain retained even when reference count reaches zero; no full-file purge button is offered.

## Validation before production use

Unit tests use synthetic files only. On a disposable migrated test database and fake attachment server, verify authorized/forbidden client and permission combinations; upload/retry/dedup/alias names; mixed original files; correction and later-month inheritance; exact-byte download; server failure; cancelled/uncertain upload; last/shared-reference deletion; fresh/stale preview; duplicate deletion retry; active send/coordinator/master-setup races; transaction rollback; legacy blockers; and preservation of queues, masters and originals. Check Batch History drawer/actions at desktop, tablet and mobile widths using mocked fixtures. Builds/unit tests alone do not prove live MySQL concurrency or configured remote-storage behavior.

Coolify redeployment and production migration remain owner-run. The owner confirmed Git push does not auto-deploy. No deployment settings were changed and no deployment/migration/real cleanup is part of local validation.

## Local validation checkpoint

Validation uses synthetic files/state only. Frontend service scenarios cover exact-byte upload-before-save, storage failure, partial multi-file failure/retry, client-scope changes, interrupted batch save, derived references and scoped deletion/download/resolution requests. Backend tests cover legacy comparisons, changed snapshots, stable-code coverage, missing/same-client parent graphs, cycles, stale-preview inputs, empty/applied drafts, queued/dispatched attempts, shared originals and authorization. The Excel aggregate is run with isolated temporary output and the existing HTTP-host access test excluded; no application host, workers, live database or real file upload/delete is started. New lifecycle authorization tests invoke route delegates entirely in memory.

Live MySQL/storage behavior and transaction races remain integration acceptance checks, not verified by these unit/service tests.
