# Excel Payslips

Open **Reports > Payroll Reports > Excel Payslips** (`/reports/payroll-reports?report=excel-payslips`). This workspace accepts salary amounts already calculated in a spreadsheet for any active client the operator is authorized to access.

## Import and mapping

1. Select the client and import an `.xlsx` or `.csv` file.
2. Check the worksheet, header row and salary month. Review excluded totals, missing-name rows and any cell errors.
3. Select an existing client salary template. Map spreadsheet columns to its components, or use manual mapping. Template components supply the payslip label and earning/deduction/employer-contribution category; template formulas and rates do not recalculate the spreadsheet amounts.
4. Map employee name, at least one earning and the explicit source net-pay column. Employee code and email are optional in the upload. Missing employee codes are allocated on save; duplicate supplied codes within a batch block saving. Preserve account numbers, UAN and other identifiers as text in the source file. An Excel serial number is not an employee code.
5. Inspect the employee preview and save the batch. Optionally save the column mapping for the same client and column-heading format next month.
6. Preview one payslip or select rows and export one combined PDF, with one employee per page. Amounts display in whole rupees by default, as requested for the source workbook; the PDF/email dialog also offers two decimal places. This changes display only, including amount-in-words, and never rewrites source amounts. The company seal is optional in the PDF action dialog. Reopen saved batches through Batch history.

Initial import uses Excel's saved results and also saves the worksheet's formulas, input values and component mapping separately. A mapped Excel error or formula without a cached value blocks import until the file is corrected/recalculated in Excel or the column/row is excluded. External workbook links are never executed. A blank mapped numeric cell is not silently treated as zero. Negative amounts and inconsistent financial totals require explicit review before PDF export or email; the imported source net pay remains unchanged.

Currency display uses Excel's 15-significant-digit precision before the selected display rounding. For example, a cached `14129.499999999998` displays as `14,130`, matching the workbook. This formatting step does not replace the imported value.

Common salary headings receive editable default mappings: employee identity, Basic/HRA/allowances, employee deductions, employer contributions, gross/deduction totals and net pay. Information such as UAN, bank account, location, attendance and rates stays separate from money. Wages become a gross total when itemized earnings are present, avoiding double-counting; billing charges and CTC are not added to earnings. These are local heading-based suggestions, not formula interpretation or a statutory rule engine. Unknown headings stay ignored for manual review. Saved client mappings and exported workbook mappings take priority; **Use suggested mapping** explicitly restores the defaults without changing the saved profile until **Save mapping** is selected.

The original PLRS September layout retains its mapping suggestion: wages are earnings, employee PF/ESI are deductions, employer PF/ESI are separate employer contributions, and bonus is information because the source net-pay formula excludes it. Monthly rate is labeled as monthly rate. These suggestions are editable and do not restrict other clients or formats. Blank codes show **Auto on save** in the import preview; a final code is allocated only when the server saves the batch.

## Create another month

1. Open a saved batch and choose **Create another month**. Select any required salary month, including an earlier month.
2. Select the source attendance column. Enter days individually, apply a value to all employees, or download and complete the attendance template. Half days are supported. The template carries the batch ID, source row and employee identity so duplicate names cannot receive another person's attendance.
3. Review **Saved components, formulas and input adjustments**. Set the month-days input cell when the source uses one, and explicitly check its calculation days. Rates remain those of the source; approved numeric input changes can be entered by cell address. Employee identifiers and formula cells cannot be overwritten through input adjustments.
4. Choose **Calculate preview**, review amounts and warnings, confirm the review and **Save new batch**. The prior batch remains unchanged. The saved batch can be reused for another month, exported or sent using existing PDF/mail actions.

The isolated calculator supports arithmetic, comparisons, percentages, same-sheet cell/range references and `SUM`, `MIN`, `MAX`, `ROUND`, `ROUNDUP`, `ROUNDDOWN`, `ABS`, `IF`, `AND` and `OR`. It calculates only dependencies of mapped outputs, including numeric information fields. Unsupported formulas, required external/cross-sheet references, circular references or missing inputs stop the preview with an error. Unused lookup errors do not block salary calculations. A values-only file cannot calculate new salary from attendance; upload a workbook containing the actual salary formulas. This is not a complete Excel calculation engine.

Batches saved before formula capture contain amounts only. Reimport their original workbook once to retain formulas; existing amounts cannot reconstruct the original calculation. Normal payroll formulas, statutory configuration and attendance records are not consulted or changed by this separate calculation. Employee Master is read only to resolve missing employee codes during save; its salary or attendance data never supplies these amounts.

## Export, edit and reimport a salary template

1. Open the required saved month from **Batch history**, then choose **Export salary template** in the page header. This downloads an editable XLSX from the saved worksheet, including its input values, formulas, employee codes and column mapping. The table's ordinary Excel export remains a list export.
2. Keep an existing employee's code unchanged. For a new employee, add the row and leave its code blank; copy the applicable salary formulas and update inputs. Do not copy another employee's code. Recalculate and save the file in Excel before uploading it.
3. Choose **Import spreadsheet**, check the restored mapping and select the intended salary month. Review new or changed columns, excluded rows and amounts before **Save batch**. Each save creates a new snapshot with its own saved-by/time; earlier batches remain unchanged. Choose the intended previous-month batch explicitly when several exist.

Missing codes first reuse a uniquely matched Employee Master record within the same client, using available PAN/UAN/Aadhaar or name plus work location. Name alone does not establish identity; conflicting or ambiguous matches require review. Supplied codes are preserved. An unmatched employee receives a code using the existing Employee bulk-upload convention: client prefix plus a padded increasing number. Allocation happens on the server against this client's Excel Payslips history and reserved Employee Master codes, under a per-client transaction lock. The resolved identifiers and added source code column are saved only in the dedicated Excel Payslips tables, with no Employee Master inserts or sequence updates. Codes appear in the saved result and subsequent exports; no master record is created. Export the newly saved batch to carry its codes into later months. Old snapshots with blank codes are not retroactively modified.

Template downloads preserve the saved worksheet's cell positions and same-sheet formulas, not the original workbook's full formatting, macros or other worksheets. References that cannot operate without missing workbook structures are exported as their cached values with explicit review warnings; these frozen inputs will not recalculate when their original external source changes. Mapping metadata is a convenience, not an authorization token. A template for another client is rejected; changed layouts and excluded rows require review. Batches without a saved worksheet still require one import of the original workbook before a formula template can be exported.

## Excel Dashboard

Choose **Excel Dashboard** in the top dashboard selector (`/dashboard/excel-payslips`). It follows the existing `reports.view` permission and client scope, and reads only Excel Payslips batches and calculation-source availability. The searchable client selector, month selector and saved-batch selector keep multiple uploads separate.

KPIs show the selected batch's payslip count, mapped earnings, employee deductions and source net pay; employer contributions and review counts remain separate. The trend uses the latest saved batch in each of the last twelve available salary months, never the sum of repeated uploads. Previous-month net change compares the selected batch with the latest batch for the preceding calendar month when it is available in that trend. The detailed employee/component variance remains in Excel Payslips. Batch links open that exact authorized client and batch, and preserve the opened selection after refresh. History retains every saved version.

The dashboard API returns compact metadata and database aggregates for at most thirteen batches (twelve trend months plus the selected snapshot), without downloading employee worksheets or invoking normal payroll/report calculation. No new schema or persistence is required for the dashboard.

## Previous-month variance

Open a saved batch and choose **Previous-month variance**. The baseline is the immediately preceding calendar month for the same client. If that month has several saved batches, choose one explicitly. If it has none, import/save that month first; the workspace does not silently substitute another month.

Employees match by a unique employee code, or by a unique combination of name and work location. Name alone is insufficient. Ambiguous identities or duplicate component labels are marked **Review**. The comparison highlights new/missing employees, added/removed components, category changes, changes in earnings/deductions/employer contributions/net pay, and information changes such as attendance or rates. Currency changes are compared at two-decimal display precision to avoid false differences from Excel's binary numeric tails; original amounts remain unchanged. Use **Changes only** or export through the existing table export control. A difference can be expected because attendance or rates changed; it is not automatically a payroll error.

## Email

Use **All / Not sent / Queued / Sent / Needs attention** to filter the saved batch. Email status badges show the actual recipient beside the employee name. Select all applies to the current tab; Email batch/selected includes only unsent rows. Refresh email status reloads saved delivery progress, and queued deliveries update every 15 seconds while the batch is open. If status cannot be verified, new sends stay disabled until a successful refresh. Unselected **PDF all** still exports the whole batch.

Email is required only when sending. Individual delivery attaches each selected employee's own PDF; a combined delivery attaches all selected payslips to one explicitly entered address. Missing/invalid recipients return errors without affecting PDF export. Recipient overrides belong to that send action and do not edit Employee Master or the saved batch.

**Background email jobs:** Send email submits the entire selection (up to 1,000 rows) in one request. The server saves the job, delivery descriptors and notification queue entries in the same transaction. After acceptance, the existing notification worker generates PDFs and sends individual messages sequentially; the page does not need to remain open. Combined delivery queues one PDF to the explicitly supplied recipient. Neither path stores PDF files.

**Email progress** remains available on reopening the saved batch, with separate Sent, Queued, Failed, Email missing / invalid, Already handled and Needs review counts. The progress fraction means **processed**, not successfully sent. A missing/invalid address is not queued; supplying it later creates a new job for the remaining rows without changing the earlier job's result. SMTP, attachment-generation and delivery failures can also need attention. Ongoing jobs refresh every ten seconds while the batch is open. A failed refresh preserves the last known progress and displays a warning.

The notification bell shows the signed-in sender's ongoing jobs and completed outcomes within their currently authorized client scope. Selecting a notification opens that exact client, batch and job. Bell progress refreshes every thirty seconds, on focus, when opened and after a send action. Completed notifications can be dismissed by their sender; the job stays in the batch's history. Saved jobs use the existing `excel_payslip_batches.send_state_json`, so this update requires no schema migration.

Job APIs: `POST /api/excel-payslips/batches/{id}/send-job?clientId=...`, `GET /api/excel-payslips/batches/{id}/mail-jobs?clientId=...`, `GET /api/excel-payslips/mail-jobs` (current sender only), and `POST /api/excel-payslips/batches/{id}/mail-jobs/{jobId}/dismiss?clientId=...`. Sending and dismissing require the existing payroll-management permission; batch progress requires the existing payslip read permission and client access. The older `/send` endpoint remains compatible with previous clients.

The existing notification queue and SMTP settings handle delivery, including paused/suppressed delivery. Queue status is not proof of inbox delivery; inspect notification delivery logs. Retrying the same send request retains its request reference to prevent duplicate queue entries. A new request also skips any row already recorded for delivery in that saved batch, including after refresh or reopening. This protection applies across individual and combined delivery and recipient changes. A combined PDF includes only previously unqueued rows, and its status shows the actual combined recipient; it does not imply delivery to each employee's own inbox.

If a submission response is lost, the retry uses the same request ID and returns the saved job instead of creating another one. A worker interrupted after SMTP acceptance but before saving its result cannot establish whether delivery occurred. Older Processing items are flagged for operator review, never automatically resubmitted by this workspace. The existing worker and SMTP behavior remain unchanged; this is durable submission and tracking, not an exactly-once inbox-delivery guarantee.

`GET /api/excel-payslips/batches/{id}/delivery-status?clientId=...` returns each row's persistent email status, recipient, queue/sent timestamps and eligibility. **Pending** means no mail has been queued, including rows initially missing an email; supplying their addresses later sends only those remaining rows. **Queued** includes automatic retries and processing; **Sent** comes from the existing queue or retained successful notification logs. **Failed** and unverifiable **Unknown** records remain protected from a fresh duplicate: review or retry the existing notification in Settings > Notifications. PDF exports remain available for every row. An all-skipped selection does not check SMTP or generate PDFs. The existing per-client and batch locks keep concurrent send actions from queueing the same rows twice. No batch snapshot, Employee Master record, schema or saved PDF is changed by this delivery-status update.

Delivery metadata stores the recipient, selected source rows, seal/rounding options, request receipt and job ownership/progress references. The worker checks the saved batch and queue reference, then generates the attachment in memory. Preview, download and email do not save generated PDFs to disk, attachment storage or the database. The static logo/seal assets remain part of the API deployment.

## Isolation and limits

- No Employee Master import, attendance calculation, pay run, payroll report or existing payslip format is updated by this workspace.
- Two dedicated tables keep this workspace separate: `excel_payslip_batches` stores client-scoped batch snapshots and delivery metadata; `excel_payslip_calculation_sources` stores the corresponding worksheet values, formulas and mapping. A batch and its calculation source save in one transaction. Saved amounts and labels remain independent of later salary-template changes. Only reusable column-mapping configuration stays in `modulesettings`; normal payroll tables are unaffected.
- Viewing/exporting reuses the Payslip Register read permissions; importing, saving mappings and sending reuse `payroll.run`, `payroll.approve` or `payroll.payments`. Every route checks client scope. Reports navigation retains the application's existing Reports access rules.
- Upload limit: 30 MB; batch limit: 1,000 employee rows / 8 MiB snapshot; calculation-source limit: 16 MiB, 512 columns and 150,000 populated cell slots; email PDF attachment limit: 10 MiB. Formula evaluation has bounded operations and recursion. Background mail jobs accept the whole selection; the legacy `/send` endpoint retains its 25-row individual-request limit. One client can retain up to 50 different column-heading mappings.
- Logo and the user-supplied signature/seal are private API deployment assets. PDF generation validates that mapped content fits a readable single page before saving a batch.

## Dedicated storage migration

Stop API instances using this database before migrating so the earlier implementation cannot write more batches into settings. From the repository root, run:

```powershell
dotnet run --project .\Payroll.API\Payroll.API.csproj --launch-profile http -- --migrate-excel-payslips
```

The command uses the selected API configuration's database connection and creates both dedicated tables from `Payroll.API/Database/ExcelPayslips.sql`. Run it again for this update even if the earlier batch-only migration was completed: the new calculation-source table is required. For legacy installations it also transfers existing `excel_payslip:<batch-id>` snapshots with their original IDs and values, verifies each copy, then removes those exact legacy settings rows in the same transaction. Mapping profiles and unrelated settings remain unchanged. Repeating the command is safe; conflicting destination snapshots stop it rather than overwrite data. The command exits without starting the API or notification workers and does not send mail. The script alone creates the schema; use the command for the verified data transfer. Migrating old batches does not invent formulas that were never stored.

If earlier `excel_payslip_mail:` or `excel_payslip_send:` records exist, migration stops for conversion review: that earlier format omitted the seal/rounding settings or batch linkage needed to reproduce delivery safely. Do not delete those records to bypass the guard. Any data transfer rolls back on failure; the empty table created by MySQL DDL may remain. No legacy PDF options are guessed.

After successful migration, start the updated API normally. Before deployment, build the API and UI. An authorized operator can then save a reviewed batch and export it. Actual SMTP delivery requires a separate intentional send; neither live migration nor SMTP delivery was exercised during this storage change.
