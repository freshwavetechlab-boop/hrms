## Current save and configuration workflow

Save updates the working Excel payslip record for the selected client and salary month. A different month remains a separate monthly record. Saved payslips lists one current record per client/month, with no version picker or batch-history workflow. Existing legacy records remain addressable internally for already-linked delivery and payroll evidence; saving does not create another revision or silently delete those references.

Unchanged source employee rows retain their IDs and reviewed negative-amount acknowledgment. Changed salary amounts get a fresh row binding so old delivery/review status cannot describe a different salary. The monthly record ID remains the same. Updates are atomic under the client lock, retain original attachment bytes, and wait for active mail delivery to finish. Identical re-uploaded originals reuse the same owned file bindings. Corrections and mapping edits update this same monthly record and never send mail.

Configure reopens its existing setup. Edit configuration, Preview calculations and Save reviewed configuration update that receipt and the selected employee salaries. Unchanged employees are not rewritten. Exact existing templates are reused; explicit updates keep the currently assigned template ID and require its complete employee scope before shared rules change. Processed/pending payroll protections and source, identity, attendance, policy and review-hash checks remain. Regular employee effective-date/audit records and delivered evidence remain separate from the removed payslip-version workflow.

Literal monetary output columns are employee input columns rather than one constant formula/template variant per amount. Source formulas are never frozen into those inputs. Different source formulas still require review. Template names no longer contain generated source/cohort IDs. The v8 mapping knowledge and retrieval regression retain this boundary.

Regular payroll has **Excel with formulas** before any run is created. It exports the selected policy roster (or the client's roster if no policy is selected), effective salary inputs, native attendance, configured formulas and eligible approved adjustments into an actual XLSX. Payroll contains editable attendance/amount inputs, raw/monthly/earned formulas, earnings/deductions/employer totals, net, and the fixed native net at download for comparison. Rules records calculation provenance. Excel recalculates after input changes and uses currency midpoint-to-even rounding consistent with the engine. Missing attendance is actionable; it is never replaced with full-month days. Live dated PF/projected TDS and aggregate location allocations are currently rejected instead of exported as frozen policy results.

Formula download now requires an attendance policy and a nonempty employee selection from that policy. The request carries the policy batch and group IDs; server validation rejects missing, foreign, stale or mismatched groups and out-of-policy employees before calculating. Saved attendance remains mandatory. The former fallback to the full client roster is removed only from this download action. The regular payroll processing paths are unchanged.

Files use `<client-name>-payroll-formulas-<YYYY-MM>.xlsx`, with filesystem-invalid characters replaced. PF/ESIC calculated cells contain native XLSX `<f>` formulas using local base/earned/day references, visible in Excel's formula bar. Synthetic native-engine fixtures cover zero, half-day, normal and full payable days, employee/employer PF and ESIC, slab pay and balancing pay. Independent spreadsheet recalculation checks baseline amounts and a changed-days result against the native engine. Fixed overrides stay explicit inputs; unsupported live dated policy results remain review items instead of frozen calculations. The v10 mapping knowledge retains this distinction. ## Import and mapping

1. Select the client and import an `.xlsx` or `.csv` file.
2. Check the worksheet, header row and salary month. Review excluded totals, missing-name rows and any cell errors.
3. Select an existing client salary template. Map spreadsheet columns to its components, or use manual mapping. Template components supply the payslip label and earning/deduction/employer-contribution category; template formulas and rates do not recalculate the spreadsheet amounts.
4. Map employee name, at least one earning and the explicit source net-pay column. Employee code and email are optional in the upload. Missing employee codes are allocated on save. A shared code is accepted for separate location payslips only when the name and a valid UAN/PAN/Aadhaar agree, no supplied identifiers conflict, and each row has a distinct work location. Other duplicate codes block saving. Each location row retains its own amounts, row ID and delivery tracking. Preserve account numbers, UAN and other identifiers as text in the source file. An Excel serial number is not an employee code.
5. Inspect the employee preview and save the batch. Optionally save the column mapping for the same client and column-heading format next month.
6. Preview one payslip or select rows and export one combined PDF, with one employee per page. Amounts display in whole rupees by default, as requested for the source workbook; the PDF/email dialog also offers two decimal places. This changes display only, including amount-in-words, and never rewrites source amounts. The company seal is optional in the PDF action dialog. Reopen the current monthly record through Saved payslips.

Initial import uses Excel's saved results and also saves the worksheet's formulas, input values and component mapping separately. A mapped Excel error or formula without a cached value blocks import until the file is corrected/recalculated in Excel or the column/row is excluded. External workbook links are never executed. A blank mapped numeric cell is not silently treated as zero. Negative amounts and inconsistent financial totals require explicit review before PDF export or email; the imported source net pay remains unchanged.

Currency display uses Excel's 15-significant-digit precision before the selected display rounding. For example, a cached `14129.499999999998` displays as `14,130`, matching the workbook. This formatting step does not replace the imported value. Source validation accepts the same IEEE number or Excel 15-significant-digit representation, preserving the raw cache and stored amount; it does not apply a cent-sized financial tolerance.

Saved mapping lookup is optional and times out after eight seconds. A missing preset uses suggestions; a failed lookup displays a review notice and leaves suggestions usable without overwriting the preset. Batch save still requires normal client authorization and valid financial/source data.

Mapping records use a client-specific private storage key, so older databases with a global module-code unique index also support multiple clients. Reads retain the same client's legacy mapping fallback; its first save copies legacy presets to the scoped record. No index change or cross-client data update is required.

Phone, mobile and contact-number headings default to Information and use the existing saved row information. The Phone column supports the shared table's search, filters and Excel export; template exports preserve phone prefixes and leading zeros as text. Older saved batches or explicit Ignore mappings are not changed automatically: map the phone column to Information when saving a revised batch, keeping existing employee codes.

When **Include company seal** is off, the PDF omits the Employer Signature placeholder and shows a muted footer: “This is a system-generated payslip and does not require a signature.” The same renderer is used for preview, download and email attachments.

**Simple salary slip** in the import/edit drawer saves the reference-style layout with that batch. It prints four paired rows: Employee Name/Department, UAN/Esic No, Designation/Number of Working Days Attended, and Account No/IFSC Code; followed by Income, Deductions, Deduction total and In Hand Salary. Rate stays informational and never increases earnings. Preview, download and email show **Rate/Day** when the saved earning formula verifies `monthly rate / calculation days * attendance`; the divisor comes from that formula's saved numeric cell or literal, never from attendance or a guessed calendar month. Existing daily rates are displayed directly. Amount-display precision applies to the daily rate too (15,414 / 30 shows 514 in whole rupees or 513.80 with two decimals). Batches without a verifiable divisor retain their original monthly/generic rate label and amount. Zero monetary components are omitted. Nonzero earnings and employee deductions retain their source amounts. Below In Hand Salary, a compact Employer Contributions table lists all saved nonzero employer contributions, including Employer EPF and Employer ESIC with their source percentages, and a Total Employer Contributions row. Amounts and percentages are read from the saved components. The company seal sits to the right. A note explains: Paid by the employer; does not reduce your In Hand Salary. The separate employee-code/client fields, phone, other information and amount-in-words are hidden only in this PDF layout; the saved information, table and exports retain them. Existing batches keep their detailed layout until an edited batch is saved with this option. The option also survives exported-template reimport and creation of another month, using existing JSON storage without a schema migration.

For simple slips, a source column explicitly labeled **UAN** is authoritative. Without that explicit choice, equal UANs collapse to one, missing markers can use a single valid number, and different valid numbers require review before saving or generating the simple PDF. This changes presentation only; all original mapped information remains stored. **Department prints the saved batch's selected client name**, as requested; work-location information remains stored. The simple PDF reuses the existing logo, company name and address header above Salary Slip/Month. Income and Deductions each have only Particulars and Amount as child headings.

Common salary headings receive editable default mappings: employee identity, Basic/HRA/allowances, employee deductions, employer contributions, gross/deduction totals and net pay. Information such as UAN, bank account, location, attendance and rates stays separate from money. Wages become a gross total when itemized earnings are present, avoiding double-counting; billing charges and CTC are not added to earnings. Matching monthly/earned headings and same-row formula references can distinguish a monthly input from its earned output; review these suggestions before saving. These suggestions are not a general Excel interpreter or statutory rule engine. Unknown headings stay ignored for manual review. Saved client mappings and exported workbook mappings take priority; **Use suggested mapping** explicitly restores the defaults without changing the saved profile until **Save mapping** is selected.

The original PLRS September layout retains its mapping suggestion: wages are earnings, employee PF/ESI are deductions, employer PF/ESI are separate employer contributions, and bonus is information because the source net-pay formula excludes it. Monthly rate is labeled as monthly rate. These suggestions are editable and do not restrict other clients or formats. Blank codes show **Auto on save** in the import preview; a final code is allocated only when the server saves the batch.

Different employee formulas can produce separate client salary-template variants. Billing totals and historical invoice claims do not become employee deductions merely because they appear in the worksheet.

## Export, edit and reimport a salary template

In **Saved payslips**, each client/month has one current working record. **Viewing** identifies the record currently open. Repeated Save updates that record; there is no Latest/Previous version selector.

Choose **Edit mapping** on a history row (or in the opened batch's header) to restore its saved worksheet, column choices, employee codes and formulas without uploading the workbook again. Change **Use as** or **Payslip label**, review the employee preview, then **Save as new batch**. The month stays fixed during this edit. Cancel makes no changes. **Save mapping preset** only saves choices for future imports; it does not revise the existing batch. Old batches and their email history remain unchanged, and the revised batch has separate email tracking. Legacy batches without a saved worksheet require the original workbook to be imported again. Existing payroll-management permissions control these edit/save actions.

1. Open the required saved month from **Saved payslips**, then choose **Export salary template** in the page header. This downloads an editable XLSX from the saved worksheet, including its input values, formulas, employee codes and column mapping. The table's ordinary Excel export remains a list export.
2. Keep an existing employee's code unchanged. For a new employee, add the row and leave its code blank; copy the applicable salary formulas and update inputs. Do not copy another employee's code. Recalculate and save the file in Excel before uploading it.
3. Choose **Import spreadsheet**, check the restored mapping and select the intended salary month. Review new or changed columns, excluded rows and amounts before **Save batch**. Each save creates a new snapshot with its own saved-by/time; earlier batches remain unchanged. Choose the intended previous-month batch explicitly when several exist.

Missing codes first reuse a uniquely matched Employee Master record within the same client, using available PAN/UAN/Aadhaar or name plus work location. Name alone does not establish identity. If name and work location match several master records without a unique identifying match, the row receives a new code instead of guessing a master identity or blocking import. Conflicting identity fields or ambiguous PAN/UAN/Aadhaar matches still require review. Supplied codes are preserved. New codes follow the existing Employee bulk-upload convention: client prefix plus a padded increasing number after the highest used code (for example, PLRS023 to PLRS024). Allocation happens on the server against this client's Excel Payslips history and reserved Employee Master codes, under a per-client transaction lock. The resolved identifiers and added source code column are saved only in the dedicated Excel Payslips tables, with no Employee Master inserts or sequence updates. Codes appear in the saved result and subsequent exports; no master record is created. Export the newly saved batch to carry its codes into later months. Old snapshots with blank codes are not retroactively modified.

Template downloads preserve the saved worksheet's cell positions and same-sheet formulas, not the original workbook's full formatting, macros or other worksheets. References that cannot operate without missing workbook structures are exported as their cached values with explicit review warnings; these frozen inputs will not recalculate when their original external source changes. Mapping metadata is a convenience, not an authorization token. A template for another client is rejected; changed layouts and excluded rows require review. Batches without a saved worksheet still require one import of the original workbook before a formula template can be exported.

## Isolation and limits

- No Employee Master import, attendance calculation, pay run, payroll report or existing payslip format is updated by this workspace.
- Two dedicated tables keep this workspace separate: `excel_payslip_batches` stores client-scoped batch snapshots and delivery metadata; `excel_payslip_calculation_sources` stores the corresponding worksheet values, formulas and mapping. A batch and its calculation source save in one transaction. Saved amounts and labels remain independent of later salary-template changes. Only reusable column-mapping configuration stays in `modulesettings`; normal payroll tables are unaffected.
- Viewing/exporting reuses the Payslip Register read permissions; importing, saving mappings and sending reuse `payroll.run`, `payroll.approve` or `payroll.payments`. Every route checks client scope. Reports navigation retains the application's existing Reports access rules.
- Upload limit: 30 MB; batch limit: 1,000 employee rows / 8 MiB snapshot; calculation-source limit: 16 MiB, 1500 columns and 150,000 populated cell slots; mapping-profile limit: 192 KiB; email PDF attachment limit: 10 MiB. Formula evaluation has bounded operations and recursion. Background mail jobs accept the whole selection; the legacy `/send` endpoint retains its 25-row individual-request limit. One client can retain up to 50 different column-heading mappings.
- XLSX cells containing only trailing formatting may extend past column 1500. In that case the importer trims the empty formatting tail to the last value, formula or error column. Worksheets already within the column limit retain their captured shape; real content beyond column 1500 still requires a narrower source.
- Logo and the user-supplied signature/seal are private API deployment assets. PDF generation validates that mapped content fits a readable single page before saving a batch.
