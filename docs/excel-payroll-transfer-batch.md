## Review flow

1. In Excel Payslips, open a saved batch with captured calculation source → Configure payroll, or use **All clients / selected batches → Review Master Setup**. Review the client, month, source version and cohort (up to 100 source rows).
2. Review employee matching/create decisions and effective date, component classifications, expected output columns, monthly/daily inputs, attendance and period-adjustment effects. New drafts use Transfer Review version 1; already-applied legacy receipts are not retroactively converted.
3. Preview. The Transfer Batch panel shows source/cell snapshot hashes, supported translation or exact blockers, component create/reuse, and comparison against all active templates for this client. Review fixed inputs without captured formulas and effective-period policy assumptions separately. These reviews cannot override an unsupported captured formula.
4. Select an exact existing template to reuse unchanged, or explicitly create a reviewed variant when no exact template exists. An exact available template blocks duplicate creation. Changed/inactive/foreign templates cannot be reused. Compare every variant, apply these decisions to the draft, and refresh preview after changes.
5. **Save Transfer Batch draft** persists the stable request/cohort and provenance in the existing `excel_payroll_setup_imports` JSON receipt. Saving a draft does not write masters. Reopen the same batch/cohort to resume it. The saved preview is not authorization for a future Apply.
6. Only after a fresh successful preview and explicit review acknowledgement, **Apply reviewed Transfer Batch** reuses the existing transactional Configure path. It may create components/templates, assign salary history, create reviewed dropdown/location values, import source-month attendance and create approved period adjustments as shown by existing Configure options. It does not create a pay run or activate unrelated policy proposals. This action has NOT been executed against user data by the agent.
7. The durable applied receipt retains source-row-to-employee mappings, component source comparisons and provenance. The status says configuration applied, regular-payroll parity not verified. Identical replay returns the existing receipt; changed settings/overlapping applied source rows remain rejected. Transaction failures do not commit a partial cohort; keep the same request ID and refresh/reconcile before retrying an uncertain outcome.
8. **Verify saved payroll** uses existing Employee simulations, not draft template arithmetic. New transfer receipts compare all source component/employer amounts, classifications, gross/deduction/benefit totals, payroll/present/payable days and net. Unexpected/missing/duplicate components or unavailable inputs prevent a match. Current observations do not mutate the durable receipt into a persisted parity certificate or approve a payroll run.

## Boundaries and prerequisites

- Exact transfer proof is deliberately limited to mapped same-row arithmetic, bounded same-row SUM, MIN/MAX, whole-amount ROUND and an explicitly captured fixed payroll-days cell. Lookup/cross-sheet/external/IF/sign-sensitive rounding and unbound dependencies are blocked. Textually different rewrites may require further supported translation even when cached numbers match. Nothing is silently replaced with a cached constant.
- Every financial source output must have a component output comparison. Component, employer, aggregate and net differences above 0.000001 block transfer preparation unless the bounded deterministic rounding proof below succeeds and its current fingerprint is explicitly reviewed. Cached-cell equality alone is not proof of a recurring rule or statutory correctness.
- Template reuse is conservative: ordered component IDs, values, calculation/formula/base, proration and rounding configuration must match. Existing configuration is never rewritten by reuse. Additional semantic equivalence is not inferred.
- Existing setup permissions (`settings.manage`, `employees.manage`, `payroll.run`) and client scope apply. Existing receipt migration remains an owner prerequisite if absent; no migration was run here.
- Existing Configure transaction locks and request/selection receipts are reused. Source/configuration changes invalidate reviewed hashes. MySQL race/rollback and global-storage integration were not exercised against a live database.
- No independently verified live counts or PLRS template comparisons are claimed. Browser layout checks are blocked by the missing configured Playwright module; see `excel-payslip-overview.md`. No software was installed or user app restarted.
- This milestone does not persist a server-verified payroll-parity certificate, auto-run attendance/payroll, provide a durable failed-attempt journal, or translate all finance workbook functions. These remain separate work. Live inspection must first verify target/environment and authorized read-only access.

## Deterministic rounding review

The existing raw comparison precision remains 0.000001. A second, bounded classification can explain a difference without increasing that precision or changing any payroll result:

- **Exact at raw precision** retains the previous amount check. Other eligibility, identity, formula, source, attendance, policy and applicability checks still apply.
- **Explained rounding** requires exact supported captured-formula translations, complete unique code/category/output-role coverage, valid source cells, and matching source versus actual core pre-currency-rounding values at the same 15-significant-digit representation boundary used by the payslip formatter. The actual core result must equal its documented 2-decimal midpoint-to-even rounding. Source totals must prove raw-component aggregation; core totals must equal its rounded component sums. Employer amounts are included. Source half-away display and core rounding differences, raw values and the final payable delta remain visible.
- **Mismatch** covers inconsistent formulas/values/totals, including an unexplained 0.001 difference even if both displayed values happen to match. A small difference is not itself evidence.
- **Unverified** covers missing legacy pre-round traces, unproven formula/input semantics, ambiguous coverage/classification and unsupported stages. Repreview the current saved batch or resolve the exact mapping/formula; there is no force-pass control.

Explained rounding requires a per-row review fingerprint followed by repreview. The fingerprint binds the saved source, request scope/effective period/formulas/day mappings and actual component calculation evidence; it excludes only the acknowledgment itself. Changed source/settings produce a different fingerprint. Apply uses the same classifier when rebuilding its locked plan and still checks the full reviewed plan hash and existing receipt/replay rules. Keep-existing decisions do not become source parity. The existing confirmed configuration Apply remains separate from Employee payroll verification.

This version proves the final component currency stage and raw-source versus rounded-core aggregation. It does not infer unknown source subtotal/ROUND stages or explain arbitrary propagation of earlier rounded dependencies. Missing proof stays blocked. No statutory rounding policy, cap, employee entitlement or historical payrun is modified. Calculation traces gain an observational `UnroundedEarned` field only; the core calculation expressions/results are unchanged.
