# API Catalog

Open **Workflows > API Catalog** for the current routes, parameters and request schemas generated by the running API. Choose **Open & test**, fill the parameters/body, then **Try it out > Execute** to see the actual response. Requests follow your login permissions. The route tables below are a reference snapshot.

## Connect a punch machine

1. Open **Settings > Leave & Attendance > Attendance**. Under **Punch machines & work locations**, save the machine ID, name and its client work location.
2. Open **Workflows > API Catalog > API keys > Generate API key**. Select that machine and generate its key. Copy the full key from the table before closing the panel. Later, the table shows a masked key, expiry and status; **Replace** or **Revoke** stops the previous key.
3. Give the machine vendor the **POST** URL shown in the catalog for `/api/integrations/attendance/punches`, the machine ID and the key. Authentication is `Authorization: Bearer <API key>`. Both IN and OUT use this one endpoint.
4. Choose **Open & test > Export document (PDF)** to download that API's URL, authentication instructions, required fields, example body and response meanings. The PDF uses the app's configured API server; export from the production deployment when sharing with the machine vendor. Copy the generated key separately.

| Field | Send this value |
| --- | --- |
| `deviceId` | Exact machine ID saved in Attendance settings |
| `punches` | Array of 1–500 punch logs |
| `punchId` | Unique machine log ID; reuse it when retrying the same log |
| `employeeCode` | Employee code from Employee Master |
| `action` | `IN` or `OUT` |
| `capturedAt` | Date/time with timezone, e.g. `2026-09-01T09:00:00+05:30` |

In **Open & test**, paste the machine API key and edit the example body before executing. The response gives a result for every punch: **Accepted**, **Duplicate** or **Rejected** (with its error). A user login token cannot submit machine punches.

Missing setup details stay in the Attendance settings list. The notification bell shows one grouped reminder containing only settings the current user is authorized to configure, within their client scope. Saved settings disappear from the list after refresh.

Use this document when configuring workflow start rules in:

`Workflow > Workflow Setup > When should workflow start?`

## Workflow Rule Cheat Sheet

For workflow configuration, you usually need these fields:

| UI field | Meaning | Example |
| --- | --- | --- |
| Screen action | Business action that needs approval | Submit payroll for approval |
| Request type | HTTP method | POST |
| Request path | API route pattern | `/api/pay-runs/{id}/submit` |
| Record type | Business object name | PayRun |
| Record number comes from | Where the ID is available | URL value |
| Record number field | Placeholder/body/query field name | `id` |
| Find client using | How client is resolved | Lookup from table |
| Table name | Table containing the record | `payruns` |
| Match this column | Column containing the record ID | `Id` |
| Client column | Column containing client ID | `ClientId` |

Recommended payroll approval rule:

## Notes For Workflow Configuration

- Prefer workflow only for meaningful business submissions, not every save.
- For URL values, request paths use placeholders like `/api/pay-runs/{id}/submit`.
- For body values, choose "Form/request value" and enter the JSON field name.
- For query values, choose "Query string value" and enter the query parameter name.
- For API-created records where the ID is returned by the API, choose "API response value".
- Prefer "Lookup from table" for client detection when the request only has a record ID.
- Avoid configuring workflow for the workflow approval endpoints themselves.
